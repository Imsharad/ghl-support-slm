01

Brief

the ask

What they ask

+

GoHighLevel wants a customer-support assistant built from an open-source small language model. They say every choice is yours. They mean it: the grade is on how you decide, not on whether you followed steps.

ObjectiveBetter than base, and reachable over HTTP

  • Fine-tune an open-source SLM on the Bitext data so it answers support questions better than the base model.
  • Self-host the result behind an HTTP API on hardware you control.
  • Use case: a customer writes in about account access, orders, refunds, payments, delivery, invoices, or subscriptions. The model answers as the support assistant: understands the request, answers accurately, keeps a support tone.
  • Measurably better. Their word. The proof matters more than the model.

DatasetBitext Gen AI Chatbot Customer Support

  • Size: 26,872 pairs, about 3.57M tokens. Kaggle: bitext/bitext-gen-ai-chatbot-customer-support-dataset.
  • Fields: flags, instruction, category, intent, response.
  • Shape: 27 intents across 10 categories. Instructions are paraphrases of the same few hundred asks. Responses are templated per intent and carry placeholders such as {{Order Number}}.
  • Leakage risk is called out in the assignment itself. Treat it as a graded item.
  • Optional: Customer Support on Twitter. Skip unless you have a specific reason and a spare day.

ConstraintsWhat they fix, what they leave open

  • License: must permit commercial self-hosting. Justify the pick.
  • Method: parameter-efficient or full fine-tuning. Justify the pick.
  • Compute: free tiers only, Kaggle or Colab. Spending money is a negative signal.
  • Serving: any HTTP stack. vLLM, SGLang, TGI, llama.cpp, Ollama, or your own.
  • AI assistants allowed. You must defend every line in the interview.

Core workFour parts, one weighted

  1. Data prep. Explore, format for the chat template, build leakage-free train / val / held-out test splits.
  2. Fine-tune. Train, log curves, document hyperparameters and what you tried.
  3. Evaluate. Marked "most important". Define better. Measure on unseen data. Compare base vs tuned, with failures.
  4. Serve. HTTP endpoint. Report latency and throughput and how you measured them.
02

Grader lens

what moves the score

What moves the score

+

Read the criteria as a skeptical engineer would. They will run your model on queries you have never seen. Your own test split is a rehearsal. Their set is the exam.

The sentence that decides the gradeThey hold an internal evaluation set and will run your model on it

Three things follow. Your model must load with a documented prompt template and one obvious command. Your reported numbers must survive contact with messier queries than Bitext contains. And a model that memorised Bitext phrasing, or that emits {{Order Number}} placeholders, will look worse than base on their set no matter what your split says.

CriterionWhat earns itWhat loses it
Evaluation rigor Held-out data the model never saw. Same prompts, same template, same decoding for base and tuned. A stated definition of better. Failure cases shown, with a reason for each. Confidence intervals or at least sample counts. Train accuracy as evidence. ROUGE against templated responses as the headline. A judge that shares a family with the model. Base run with the wrong chat template so it looks bad.
ML judgment Model size argued from VRAM and latency. Method argued from compute. Hyperparameters with a reason and a record of what you tried. One deliberate ablation. A notebook copied from a blog with the defaults left in. A 7B model because bigger. No mention of what you rejected.
Systems thinking An endpoint that answers on the recording. p50 and p95 latency, tokens per second, concurrency stated, hardware stated, script in the repo. A notebook cell that calls model.generate. Numbers with no method. A quantised demo model that differs from the evaluated one and nobody says so.
Reproducibility One README path from clone to endpoint. Pinned dependencies. Seeds. Split files committed or regenerable by hash. Hidden Colab state. Paths to your Drive. A split that changes each run.
Code quality Small modules: prepare, train, eval, serve. Config in one place. Functions a reviewer can read in an hour. One 800-line notebook. Copy-pasted eval loops. Secrets in code.
03

Decision map

5 decisions

Model, method, data, eval, serve

+

Each card lists the live options and marks one as recommended for a free-compute, seven-day sprint. The mark is a default, not a rule. If you change it, write the reason into the README, because the reason is what they grade.

Model Which base model Qwen2.5-1.5B-Instruct
Model
Which base model

Size must fit a T4 for training and a laptop for serving. License must allow commercial self-hosting without a phone call.

  • RecommendedQwen2.5-1.5B-Instruct (Apache-2.0). Strong instruct baseline, standard chat template, fits QLoRA on a 16 GB T4 with room, serves at usable speed on a laptop CPU or Apple silicon via GGUF. A better base makes the base-vs-tuned bar higher, which is honest and defendable.
  • AlternativeLlama-3.2-3B-Instruct (Llama 3.2 Community License). Permits commercial use under 700M monthly active users, with attribution terms. More headroom, slower to train and serve. Pick only if you want the Llama story in the interview.
  • AlternativeQwen3-1.7B (Apache-2.0) or SmolLM2-1.7B-Instruct (Apache-2.0). Fine choices. Qwen3 needs thinking mode disabled in both training and serving templates, which is one more thing to get wrong.
  • AvoidQwen2.5-3B-Instruct ships under the Qwen Research License, not Apache. It fails the commercial-self-host requirement on its own. Check the license file of whatever you pick, not the family name.

SizingA 1.5B model in 4-bit holds about 1 GB of weights. QLoRA with sequence length 512 and micro-batch 8 stays under 8 GB on a T4. Full fine-tuning of 1.5B with an Adam optimizer needs roughly 24 GB, so it is out on free compute. T4 has no bfloat16, so train in fp16 with fp32 LoRA weights, or use Unsloth which handles this.

Method How to fine-tune QLoRA
Method
How to fine-tune

Free compute decides most of this. What is left is rank, targets, and the loss mask.

  • RecommendedQLoRA, 4-bit base, LoRA on all attention and MLP projections. Start at r=16, alpha=32, dropout=0.05, lr=2e-4, cosine schedule, 3% warmup, 2 epochs, effective batch 16, max length 512. Loss on assistant tokens only. Train with TRL SFTTrainer, or Unsloth on Colab for a 2x speed-up on T4.
  • AlternativeLoRA in fp16 without quantising the base. Fits a 1.5B model on T4 and removes one source of numerical noise. Slightly better quality, slightly more memory. A fair pick if the 4-bit run looks unstable.
  • AvoidFull fine-tuning. Does not fit free VRAM at any useful size, and on 27 templated intents it overfits faster than LoRA. Say this in the README as a considered rejection, not an omission.

AblationKeep one cheap comparison: r=8 vs r=16, or 1 vs 2 epochs. One is enough. It shows you looked, and it gives you a real answer to "why these hyperparameters".

Data What to train on, how to split Group, then stratify, then split.
Data
What to train on, how to split

The dataset is a few hundred distinct asks, each paraphrased dozens of times. A random split leaks by construction.

  • RecommendedGroup, then stratify, then split. Normalise each instruction (lowercase, strip punctuation, collapse whitespace). Cluster near-paraphrases with MinHash or embedding cosine above 0.9. Assign whole clusters to one split. Stratify by intent so all 27 appear in each split. Aim for 80 / 10 / 10. Freeze the test split on day one and do not open it until the final eval.
  • RecommendedRewrite placeholders. Replace {{Order Number}}, {{Website URL}} and friends with natural phrasing ("your order number", "our website") in a single deterministic pass. Keep the map in the repo. Otherwise the tuned model emits curly braces on their held-out set.
  • RecommendedWrite your own 40 to 60 messy queries. Typos, two intents in one message, missing context, an angry tone, an off-topic ask. This is your proxy for their internal set. Never train on it. It is the eval that will predict your real grade.
  • AlternativeSubsample train to 8 to 10k rows if training time is tight. Paraphrase-dense data gives little per extra row. Document the number you used.
  • OptionalTwitter data. Adds realism and noise. Costs a day of cleaning and confounds the base-vs-tuned story. Cut it and say why.

PromptUse the model's native chat template with a short fixed system prompt, for example "You are a customer support assistant. Answer clearly and helpfully." Store the exact string in configs/prompt.txt and load it from there in train, eval, and serve. One source, three consumers.

Eval What better means, and how to show it Three layers, all on held-out data.
Eval
What better means, and how to show it

This is the graded part. Define better before training. Run base first so the harness is tested and the baseline is fixed before you can be tempted.

  • RecommendedThree layers, all on held-out data. (1) Intent coverage: does the response address the right intent? Score with a small classifier trained on responses, or a judge with the intent list. (2) Judge rubric, pairwise: base vs tuned on the same prompt, judge scores 1 to 5 on correctness, helpfulness, tone, and brevity, with position swapped to cancel order bias. Report win / tie / loss and a bootstrap interval. (3) Hand-reviewed failure gallery: 10 to 15 cases where tuned loses or both fail, each with one sentence on why.
  • RecommendedSame everything. Same system prompt, same chat template, greedy decoding or a fixed seed, same max tokens, for both models. State it in one line in the README so nobody has to ask.
  • SupportingReference similarity (ROUGE-L, BERTScore) on the Bitext test split. Fine as a secondary number. It rewards template matching, so never lead with it, and say so.
  • JudgeUse a bigger model from a different family than the one you tuned. A local Llama-3.1-8B via Ollama costs nothing and keeps the "no spend" rule. Spot-check 30 judge verdicts by hand and report agreement.

Two test setsReport the Bitext held-out split and your own messy set as separate tables. If tuned wins big on the first and small on the second, say so. That gap is the most honest sentence in the whole submission, and the one their held-out set will confirm.

Serve Where the endpoint lives Merge LoRA, export GGUF, serve with llama.cpp or Ollama.
Serve
Where the endpoint lives

Free GPU notebooks cannot hold a public endpoint. Your laptop can. Pick the stack that gives a live demo and a clean benchmark.

  • RecommendedMerge LoRA, export GGUF, serve with llama.cpp or Ollama. Merge the adapter into the base in HF format, convert to GGUF at Q8_0 (closest to the evaluated model) and Q4_K_M (fastest). Write an Ollama Modelfile whose TEMPLATE matches the training template exactly. Serve the OpenAI-compatible /v1/chat/completions route. Runs on a MacBook, records well on Loom.
  • AlternativevLLM with --enable-lora on a Kaggle T4, tunnelled with ngrok for the demo. Better throughput numbers, more moving parts, and the tunnel dies with the notebook.
  • AlternativeFastAPI + transformers on CPU. Simplest to read, slowest to run. Acceptable if the numbers are reported honestly.

BenchmarkA script in serve/bench.py: 100 fixed prompts, concurrency 1 and 4, record p50 and p95 end-to-end latency and output tokens per second. Print hardware, quantisation, and context length beside the numbers. Ship the raw JSON.

Pipeline

data → train → eval → serve → submit

Day-by-day order

+

The order matters. The eval harness is built and run against the base model before training starts. That gives a fixed baseline, a tested harness, and no chance to tune the metric to the result.

Step 01Data preparationDay 1
  1. 01

    Data preparation

    Day 1data/prepare.py

    Download from Kaggle. Profile intents, lengths, flag codes, placeholder tokens. Rewrite placeholders. Cluster paraphrases. Split by cluster with intent stratification. Write three JSONL files in chat format plus a splits.json with row ids and the clustering threshold.

    • Check: no normalised instruction appears in more than one split. Assert it in code.
  • Check: every intent has at least 20 test rows.
  • Write the 40 to 60 messy queries into data/ood_queries.jsonl tonight, before you have seen any model output.
    • GateTest split hashed and committed. You will not open it again until step 04.
    Step 02Eval harness, run on base firstDay 1 to 2
    1. 02

      Eval harness, run on base first

      Day 1 to 2eval/run_eval.py · eval/judge.py

      Load the prompt template from one file. Generate base-model answers for the validation split and the messy set with greedy decoding. Run the intent scorer and the judge. Save every generation to disk with the config that produced it.

      • Result: a baseline table you will never have to re-run, and a harness that already found its own bugs.
  • Sanity: read 20 base outputs by hand. If base is already good on Bitext, the bar is high and you should say so early.
    • GateBaseline numbers written into a dated file under eval/results/.
    Step 03Fine-tuneDay 2 to 3
    1. 03

      Fine-tune

      Day 2 to 3train/train.py · configs/lora.yaml

      QLoRA on Colab or Kaggle T4. Log train and validation loss every 50 steps to a CSV and a plot. Checkpoint to Drive or Kaggle output every 200 steps, because free sessions drop. Push the adapter to the Hugging Face Hub when done.

      • Expect validation loss to fall fast and flatten within one epoch on templated data. A rising validation loss in epoch 2 is overfitting. Stop there.
  • Run the ablation (rank or epochs) while writing the README. Keep the loser's curve. It is evidence.
  • Merge the adapter into a full HF checkpoint too. Graders load merged weights with fewer surprises.
    • GateAdapter on the Hub. Loss curves as PNG in train/runs/. Config file matches what ran.
    Step 04Evaluate tuned vs baseDay 3 to 4
    1. 04

      Evaluate tuned vs base

      Day 3 to 4eval/results/ · eval/failures.md

      Open the test split once. Run the exact harness from step 02 on the tuned model. Same prompt, same decoding. Produce: intent coverage for both models, pairwise judge win / tie / loss with a bootstrap interval, the secondary reference-similarity table, and the messy-set table beside the Bitext table.

      • Failure gallery: 10 to 15 rows, each with query, base answer, tuned answer, judge verdict, and one sentence on the cause.
  • Judge check: hand-label 30 pairs yourself and report agreement with the judge.
  • Quantised check: run the Q8_0 GGUF on the messy set too. Report the drift, if any, next to the fp16 number.
    • GateOne results table that a stranger can read in two minutes. If tuned does not win on the messy set, that is a finding, not a failure. Write it down.
    Step 05Serve and measureDay 4
    1. 05

      Serve and measure

      Day 4serve/Modelfile · serve/bench.py

      Convert merged weights to GGUF. Write the Ollama Modelfile with the same system prompt and template. Start the server. Send one curl. Then run the benchmark script at concurrency 1 and 4 and save the JSON.

      • Report: hardware, quantisation, p50, p95, output tokens per second, prompt set, how many runs.
  • Also ship serve/inference.py that loads the HF adapter with transformers and answers one query. That is the path the graders will use.
    • GateA curl command in the README returns a support answer from the tuned model.

      • Fresh clone test: on a clean machine or container, follow the README top to bottom. Fix what breaks.
  • Submit: repo link, Loom link, README, weights link. Four items.

    05

    Leakage & traps

    8 ways to fail their set

    Eight ways to fail their set

    +

    Each of these produces a submission that looks good in its own README and falls over on the internal held-out set or in the interview. Most cost minutes to avoid and hours to explain later.

    Trap 01Paraphrase leakage
    Trap 01

    Paraphrase leakage

    Bitext has a few hundred asks, each phrased dozens of ways. A random 80 / 10 / 10 split puts "how do I cancel my order" in train and "how can I cancel my order?" in test. Any metric on that test set measures memory.

    FixCluster before splitting. Assert that no normalised instruction crosses splits. Say the threshold in the README.

    Trap 02Template mismatch
    Trap 02

    Template mismatch

    You train with one chat template, evaluate with another, and serve with a third written by hand in an Ollama Modelfile. The model that answered your eval is not the model on the endpoint, and neither is what the graders will load.

    FixOne configs/prompt.txt. Print the fully rendered prompt once in each stage and diff them.

    Trap 03Placeholder echo
    Trap 03

    Placeholder echo

    Bitext responses contain {{Order Number}}, {{Website URL}}, and similar. Train on them raw and the tuned model will answer a real customer with curly braces. On their held-out set that reads as broken.

    FixReplace placeholders with natural phrasing in data prep. Keep the mapping in the repo and mention it in the README.

    Trap 04Metric theater
    Trap 04

    Metric theater

    Train accuracy, ROUGE against templated references, or a judge from the same family as the tuned model. Each can show a large gain that means nothing. A skeptical engineer will pick the weakest metric and ask why it is the headline.

    FixLead with pairwise judge results on unseen data, with intervals. Report ROUGE second and label its weakness yourself.

    Trap 05Crippled baseline
    Trap 05

    Crippled baseline

    Running the base model without its chat template, or with a different system prompt, or with a shorter token limit, makes it look worse than it is. This is the first thing a reviewer checks and the fastest way to lose trust.

    FixSame template, same system prompt, same decoding, same limit. Show three raw base outputs in the README so the reader can see it was fair.

    Trap 06Demo-only model
    Trap 06

    Demo-only model

    You evaluate the fp16 adapter, then serve a Q4 GGUF on the Loom, then upload only the adapter. Three artefacts, one set of numbers, and no statement of which is which.

    FixName every artefact and say which number came from which. Run the messy set on the GGUF too and report the drift.

    Trap 07Overfit to the template, brittle on the wild
    Trap 07

    Overfit to the template, brittle on the wild

    Two or three epochs on 27 templated intents makes a model that answers Bitext paraphrases perfectly and freezes on a two-intent message with a typo. Their internal set is closer to the wild than to Bitext.

    FixStop when validation loss flattens. Keep the learning rate modest. Judge on your messy set and let that number decide the checkpoint.

    Trap 08License and hardware surprises
    Trap 08

    License and hardware surprises

    Qwen2.5-3B is research-licensed. Gemma has its own terms. A T4 has no bfloat16, so a bf16 config silently falls back or overflows. Colab kills a session at hour 4 and takes the unsaved adapter with it.

    FixRead the license file of the exact checkpoint. Train in fp16 with fp32 LoRA weights. Checkpoint to Drive every 200 steps.

    Interview defense

    what they will ask

    Q&A shapes for the interview

    +

    AI assistants are allowed. The price is that you can defend every choice without notes. Each question below has the shape of a good answer. Fill in your own numbers.

    Q1Why this model and this size?

    Shape: license first, then VRAM, then latency. "Apache-2.0 removes the legal question. 1.5B in 4-bit trains on a T4 with headroom and serves at N tokens per second on my laptop. A 3B would cost 2x on both and the task is 27 intents, not open-ended reasoning."

    Have the rejected options ready: the 3B research license, the 7B that does not fit free compute.

    Q2How do you know there is no leakage between train and test?

    Shape: describe the clustering, the threshold, the assertion, and what happened when you tried a random split. "Random split gave X on the judge. Cluster split gave Y. The gap is the leakage."

    If you did not run the random split for comparison, run it. It takes ten minutes and is the strongest single answer in the interview.

    Q3Your judge is an LLM. Why should we trust it?

    Shape: different family from the tuned model, position-swapped pairs, and a hand-labelled sample with an agreement number. "I labelled 30 pairs blind. Agreement with the judge was Z. Disagreements were mostly ties."

    Concede the limit: an LLM judge favours longer, more polite answers. Say what you did about length.

    Q4What happens on our held-out set?

    Shape: point at the messy-set table. "My own out-of-distribution set is my best guess at yours. Tuned beat base by N there, less than the Bitext gap of M. I expect your number to sit closer to N. Here is why."

    Name the known weakness: multi-intent messages, or questions outside the 27 intents. Show one failure from the gallery.

    Q5Why these hyperparameters?

    Shape: starting point, the one ablation, the curve. "r=16 is the common default for a 1.5B model. I tried r=8, it was within noise, so I kept 16. Two epochs: validation loss flattened at 1.3 and rose after, so I stopped."

    Q6Is the model on the endpoint the model you evaluated?

    Shape: list the artefacts and the number attached to each. "Eval numbers come from the fp16 merged checkpoint. The endpoint runs Q8_0 GGUF. I re-ran the messy set on the GGUF and it moved by D. The Hub link is the merged checkpoint."

    Q7What would you change for production?

    Shape: pick three and be concrete. Retrieval for account-specific facts instead of templated answers. Guardrails for off-topic and refund-policy questions. A proper human eval loop with support agents. Batching and a real GPU behind vLLM with a p95 target.

    RealYou ran it, the number is in the repo

    • Cluster-based leakage-free splits, with the assertion.
    • QLoRA run with logged curves and one ablation.
    • Base vs tuned on two held-out sets, pairwise judge, intervals, failure gallery.
    • A working endpoint with a benchmark script and raw results.
    • A fresh-clone reproduction of the README.

    Cut for timeYou know it matters and you chose not to

    • Human eval beyond yourself. Say what it would cost and who would do it.
    • A hyperparameter sweep. One ablation instead.
    • Twitter data. Realism versus a clean base-vs-tuned story.
    • Multi-turn conversations. Bitext is single-turn.
    • Preference tuning on the failure gallery. The obvious next step, and the interview answer to "what next".
    • GPU serving with batching. Laptop numbers are honest, not impressive.

    The word cut is not an apology. It says you saw the whole shape and chose the seven-day slice. Write each cut with its cost and its trigger for revisiting.

    Research thesis

    from X · Sep 2026

    Tobi / flywheel thesis

    +

    What the live discourse says about fine-tuning small models for custom tasks. This is the method thesis behind the decision map above — not a replacement for eval rigor.

    The sentenceNarrow task + tiny model + recursive data flywheel beats rented frontier on that task

    Shopify’s @tobi (1 Sep 2026): a finetuned 0.8B beat GPT-5.6-sol xhigh on buyer-profile building after a self-improving loop. Prompt 9.1k→1.1k tokens. Throughput ~2M→72M/day. The model is the exhaust; the loop is the engine. Open infra: tangleml.com.

    What this means for GHLSpecialize, don’t chase size

    • Bitext is already a narrow domain: 27 support intents.
    • A 1.5B–3B QLoRA SFT is the right shape — same thesis as 0.8B specialists.
    • Optional stretch if time: preference pass (DPO) on failure pairs, or a tiny on-policy distillation loop from a stronger teacher on synthetic support traces.
    • Do not skip the held-out messy set. Flywheels without honest eval are metric theater.

    Default stack from discourseWhat people actually ship

    pick base (0.5B–4B) → curate / rewrite domain data → QLoRA SFT (Unsloth / TRL) → optional DPO / GRPO if rewards are checkable → merge → GGUF → Ollama / llama.cpp
    • Tooling radar: Unsloth, LLaMA-Factory, TRL, Axolotl, MLX.
    • PEFT tip of spear: NoRA (normalize LoRA’s A at init) — optional try if easy to swap.
    • Distill tip of spear: on-policy distillation (OPD), then RL — sequential beats joint.

    Methods from X

    cutting-edge cluster

    PEFT, OPD, GRPO, tooling

    +

    Fan-out across PEFT, tooling, preference/RL, and distillation. Filtered for what transfers to a free-compute customer-support SLM.

    PEFTBeyond plain LoRA

    PEFTBeyond plain LoRA

    • QLoRA / 4-bit — still the default for free T4 / Colab.
    • DoRA — claimed better than LoRA in some applied posts (TTS, adapters).
    • NoRA (arxiv 2608.31036) — normalize A along rank; NoRA-init gets most of the gain. Worth a one-line README mention if you try it.
    • Also in circulation: LoRA+, VeRA, rsLoRA, PiSSA — treat as optional ablations, not day-1 work.
    Preference / RLWhen the answer is checkable

    Preference / RLWhen the answer is checkable

    • DPO — lightweight after SFT if you build preference pairs from failures.
    • GRPO — hot for math/code/browser with verifiable rewards; less natural for open support chat unless you invent a reward (intent match + placeholder-free + length).
    • Watch reward hacking (try/except on code rewards is the classic cautionary tale).
    Distillation / dataTeacher → student

    Distillation / dataTeacher → student

    • Synthetic teacher traces then SFT/DPO/RL on the SLM.
    • OPD (on-policy distillation): student rollouts + teacher token supervision. New papers claim 1–16 queries ≈ full-data coverage; bottleneck is absorption rate.
    • OPD-then-RL beats mixing distillation and RL in one loss.
    • Gemma 270M recipe: synthetic task data + LoRA + INT4 → on-device.
    Production flywheelsShopify / Liquid

    Production flywheelsShopify / Liquid

    • Shopify ICML: mine low-scoring conversations → critique → repair → retrain → compress prompts. GraphQL agent cost −96%.
    • Liquid nanos: tiny enterprise specialists; 90→100 reliability is the hard part.
    • TangleML: open-sourced core of Shopify’s self-improving loops.

    Adopt now vs stretch

    +

    Keep the decision map’s free-compute defaults. Borrow the research thesis where it raises the grade without blowing the week.

    Adopt nowIn the 7-day slice

    • Thesis language in README: “specialist SLM for 27 support intents,” cite the Tobi / Shopify pattern as motivation, not as a claim you replicated their flywheel.
    • Qwen2.5-1.5B + Unsloth QLoRA — matches discourse default and brief recommendation.
    • Placeholder rewrite + cluster splits + messy OOD set — your stand-in for “held-out reality.”
    • Eval first on base — same discipline as Shopify mining failures before retraining.
    • Merge → GGUF → Ollama — serve path already in decision map.

    Adopt if aheadStretch, then cut honestly

    • DPO on 200–500 preference pairs from failure gallery (tuned-bad vs rewritten-good).
    • One NoRA-init trial if Unsloth/PEFT swap is one config line.
    • Synthetic hard negatives from a larger teacher (multi-intent, angry, off-policy) — never mix into the frozen test set.
    • Do not attempt full Shopify flywheel / TangleML / GRPO math pipelines in week one. Name them under “what next / production.”

    Interview lineConnect research to choices

    “The industry pattern right now is specialized small models with a data loop beating frontier on narrow tasks — Shopify’s 0.8B buyer-profile result is the clearest public example. This take-home is that pattern at homework scale: Bitext is the narrow task, QLoRA is the cheap adapter, my messy set is the held-out reality check, and the endpoint is how you verify it.”

    2. Stemming bug: finetune ≠ finetuned

    3. Semantic search biased to tutorial jargon

    4. Prevention rule
